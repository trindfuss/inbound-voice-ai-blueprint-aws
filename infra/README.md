# OwlBank infra (AWS CDK, Python)

The AWS side of the OwlBank inbound voice blueprint. It is a separate uv project, so the application's dependencies and the CDK's stay apart.

Synth and the tests run offline: no AWS credentials, no lookups, no deploy. The account is a fake default (`111111111111`) unless `accountId` is set. You don't need a system Node.js or the npm CDK CLI: the `nodejs-wheel-binaries` dependency provides `node` for jsii inside the venv, pinned below 25 to a release jsii supports, and it is used even when another `node` is on `PATH` (`owlbank_infra/node_bootstrap.py`). The npm CDK CLI (`npx aws-cdk@2`, for deploys) runs on the system Node.

## Conventions

- **Paths.** `repo` is the repository root and `infra` is `infra/`. Each command says which one it runs from.
- **Credentials.** Commands use the AWS credentials in your environment. Export `AWS_PROFILE=<profile>` (and `AWS_DEFAULT_REGION` if the profile has none) in every shell you use for these steps: `populate_secrets`, `check_secrets`, `twilio_setup`, `seed`, `masking`, `web_activity` and the other scripts have no `--profile` flag, and the first-deploy `cdk` and `aws` commands carry none, so they read the environment. `preflight.py`, `check_resolver.py`, `call_timeline.py` and `push_bridge_image.py` also take `--profile`; the examples show it, and with `AWS_PROFILE` exported you can leave it out. Temporary credentials expire, and a long deploy can outlast them: when a command reports expired credentials, renew them the way your organization does.
- **Context flags are not remembered.** The CDK keeps no `-c key=value` between runs, and an omitted key goes back to its default. Pass your full flag set on **every** deploy of every stack that reads it, including a stack deployed as a dependency (a stack is deployed alone only with `--exclusively`), and run `cdk diff` first. In zsh, write the flags inline or in an array: a variable holding flags reaches the CDK as one argument and the context is lost. This is "the context rule" in the rest of this file. The `twilioPhoneNumber` flag is part of it: pass it on every deploy that includes `OwlBankBridge`, directly or as a dependency.
- **Reseeds.** `scripts/seed.py` keeps some live settings and overwrites others; the rules are in the "What a reseed keeps" paragraph under "Deploying a change".
- **Terms.** *TAC* is Twilio Agent Connect, the library the bridge uses to talk to Twilio. *CMK* is the customer-managed KMS key `alias/owlbank-data` that `OwlBankData` creates. *Orchestrator* is Twilio Conversation Orchestrator, which holds the conversation, and *Memory* is its profile store. *ConversationRelay* streams the call's speech as text to the bridge. The *AgentCore harness* is AgentCore's managed agent loop, which this solution does not use (see the production guide, "Why not the AgentCore harness?"). *Phase pre* and *phase post* are `scripts/twilio_setup.py --phase pre` (Twilio setup that needs no domain, run before the stacks) and `--phase post` (the webhooks, run after the stacks).

## Commands

```bash
cd infra
uv sync
uv run python app.py
uv run pytest -q
```

`uv sync` runs once. `app.py` synthesizes all stacks to `cdk.out/` (cdk-nag runs here). `pytest` covers synth, policy assertions, cdk-nag and schema parity.

The deploy helpers in `infra/scripts/` are `preflight.py`, `push_bridge_image.py`, `build_lambda_deps.py` and `resolve_models.py`; the operator scripts in `scripts/` (repository root) are `seed.py`, `populate_secrets.py`, `check_secrets.py`, `twilio_setup.py`, `deploy_flex_plugin.py`, `assign_agent_skills.py`, `prompt_suite.py`, `check_resolver.py`, `hash_tool.py`, `masking.py`, `call_timeline.py`, `memory_history.py`, `web_activity.py` and `rehearse_human_leg.py`.

`app.py` reads its context from `cdk.json` and `-c` flags. Tests pass context to `owlbank_infra.app_builder.build_app(context)` directly.

## Two exposure modes

Chosen by whether `domainName` is set.

| | CloudFront mode (no `domainName`; the default, for dev and test) | Custom-domain mode (`domainName` + `certificateArn`; the production recommendation) |
|---|---|---|
| Bridge WebSocket | CloudFront distribution on `d....cloudfront.net` (default certificate), CLOUDFRONT-scope WAF, a **VPC origin** to an **internal** ALB in the private subnets | Public ALB in the public subnets, HTTPS listener (ACM, TLS 1.3 policy), regional WAF |
| ALB listener and security group | HTTP 80 only. Ingress: port 80 from the CloudFront origin-facing managed prefix list, nothing else. No `0.0.0.0/0` anywhere in ingress. **Second control:** the VPC origin sends a secret header `X-Origin-Verify`, and the listener's default action is a fixed **403**; one rule at priority 1 forwards only when the header matches. The prefix list alone admits every CloudFront distribution in every account; the header is what ties the ALB to this deployment's distribution | HTTPS 443 from `0.0.0.0/0` (Twilio's IPs are dynamic) |
| CloudFront to ALB hop | **HTTP** (the ALB has no certificate). **Unencrypted**, for dev and test only (see "The unencrypted hops" below) | n/a (TLS at the ALB) |
| API Gateway | default `execute-api` endpoint **on**, with regional WAF, stage throttling, Basic auth and the signature check | `voice.<domain>`, `execute-api` **off** |
| Region | `us-east-1` only (CloudFront WAF lives there); synth fails otherwise | any |
| Outputs | `RelayDomain` (the CloudFront domain), `ApiDomain` (the execute-api host), `ApiStage` | `RelayDomain`, `AlbDnsName`, `ApiDomain`, `ApiDomainTarget` |

The bridge learns its public host from the container variable `TWILIO_VOICE_PUBLIC_DOMAIN` (TAC's own setting, see "Terms"; a plain variable, not a secret), set from the distribution domain or from `relay.<domain>`. It pins `X-Forwarded-Host` to it and checks the WebSocket signature against `wss://<that host>/ws`.

### The origin-verify header

A secret `owlbank/<stage>/bridge/origin-verify` (Bridge stack, the CMK, generated by Secrets Manager: 48 characters, no punctuation, never in a template, not populated by a script) feeds two places through the same `{{resolve:secretsmanager:<arn>:SecretString:::}}` dynamic reference: the distribution's origin custom header `X-Origin-Verify`, and the ALB listener rule's `http-header` condition. CloudFormation resolves it when it creates or updates those resources. **Check on the first deploy** that the header resolves and the ALB forwards: a request through the distribution succeeds, while the listener's default action answers 403 to any request without the header. The ALB's own health checks go from the load balancer to the targets and never pass through listener rules, so the target group's `/health` check is unaffected. Rotation and its trade-offs are in the [production guide](../docs/production-guide.md) (section 3): rotate by writing a new secret version and redeploying with `originVerifySecretVersion=<VersionId>`.

### The unencrypted hops (CloudFront mode)

The CloudFront mode, meant for **dev and test only**, uses plain HTTP on one hop: **CloudFront to the ALB (port 80)**. That is acceptable there because it stays inside AWS's network and the private subnets, the ALB is internal and gated by the origin-facing prefix list plus the secret origin header, and call tokens travel KMS-sealed, never in the clear on this hop (the traffic is call text and prompts). It is an exception to the encrypt-in-transit rule.

**Production requires** the custom-domain mode (`domainName` + `certificateArn`) with HTTPS to the ALB. `stage=prod` without `domainName` **fails synth** with an error that says so. On Fargate, in every exposure mode, the ALB talks HTTPS to the task on 8080 with a self-signed certificate the task makes in memory at start-up. The ALB does not validate target certificates, so this encrypts the hop but does not authenticate the task. On AgentCore hosting the Runtime fronts the container over HTTP, unchanged.

## Two bridge hostings (`bridgeHosting`)

`bridgeHosting=fargate` (the default) is everything above. `bridgeHosting=agentcore` runs the **same bridge image** (`src/tac_bridge/Dockerfile`, arm64, the same Strands loop) as an AgentCore Runtime. AgentCore Runtime is only a host here; it is not the AgentCore harness (see "Terms" above). When to choose each: production guide, "Hosting options for the bridge". **Fargate is the default** (WAF and the Twilio signature on the WebSocket); `agentcore` is opt-in, for example for lower-cost low-volume testing.

| | `fargate` (default) | `agentcore` |
|---|---|---|
| Where the bridge runs | ECS Fargate tasks behind the ALB (either exposure mode above) | `AWS::BedrockAgentCore::Runtime` `owlbank_<stage>_bridge`, DEFAULT endpoint only; one microVM per call, session ID = the CallSid |
| WebSocket URL in the TwiML (Twilio's XML call instructions) | `wss://<relay host>/ws?n=<nonce>`; the bridge checks the Twilio signature, then the nonce | A SigV4 pre-signed `wss://bedrock-agentcore.<region>.amazonaws.com/runtimes/<encoded Runtime ARN>/ws?...` minted by the front door for each connect, valid at most 300 s, signed with credentials of the role `owlbank-<stage>-relay-presign`. The nonce travels as `<Parameter name="n">`, because AgentCore forwards no query parameters to the container. The bridge checks the binding (the Runtime session-ID header, `setup.callSid` and `customParameters.callSid` are equal, and the process is pinned to its first session), then the nonce |
| Exposure | CloudFront or a public ALB, both with WAF | The AWS-owned AgentCore endpoint, IAM (SigV4) only; no WAF in front |
| Image | Built by `cdk deploy` (Finch, `CDK_DOCKER=finch`) | Pushed to `OwlBankBridgeImage`'s ECR repository by `infra/scripts/push_bridge_image.py`, referenced by digest (`-c bridgeImageDigest=sha256:...`) |
| Start of a call | n/a | The front door invokes `runtime_warmer` (Event) on a new call's `incoming`; it calls `InvokeAgentRuntime` with `{"action": "prewarm"}` on the call's session, so the microVM boots during the IVR |
| End of a call | The task keeps running | `/voice/status` calls `StopRuntimeSession` once per call; if that fails, the idle timeout (`agentcoreIdleTimeoutSeconds`) stops the session |
| 60-minute WebSocket cap | n/a | AgentCore closes the socket at about 60 min 57 s; `connect-action` reconnects silently (`relay_reconnect reason=stream_limit`), at most 4 times per call |
| Orchestrator status callback (`twilio_setup.py --phase post`) | `https://<RelayDomain>/webhook` on the bridge | `https://<user>:<password>@<api>/voice/orchestrator` on the front door: acknowledged and logged, not forwarded |
| Network | `OwlBankNetwork` (VPC, NAT, flow logs) | `agentcoreNetworkMode=vpc` (default): the private subnets whose AZ ID AgentCore supports, and a security group with egress on TCP 443 only and no ingress. `public`: no VPC, and `OwlBankNetwork` is not in the app |
| Bridge logs | `/owlbank/ecs/tac-bridge` | `/aws/bedrock-agentcore/runtimes/<RuntimeId>-DEFAULT`, created by the stack with the CMK and the stage's retention (`RuntimeLogGroup` output); the warmer logs to `/owlbank/lambda/runtime_warmer` |
| Bridge to Compute | SSM String parameter `/owlbank/<stage>/bridge/relay` = the relay host | The same parameter = the Runtime ARN |

Also in `agentcore`: `reuseConversation=true` is required (synth fails otherwise, naming both keys: without Orchestrator's `CLOSED` event a re-entry on a new conversation finds a stale session). The Runtime has no customer-managed key (CloudFormation has no key property on it; AgentCore encrypts its data with AWS-owned keys); its log group and the ECR repository use the CMK. The Fargate resources that are `RETAIN` with a fixed name stay in the Bridge template, dormant: the origin-verify secret (CloudFront mode) and, at `stage=prod`, `/owlbank/ecs/tac-bridge` and the bridge's `aws-waf-logs-owlbank-prod-*` group.

## Stacks

Stack order: Data, Network, Agent, BridgeImage, Bridge, Compute, Api, then the optional Admin.

| Stack | Purpose |
|---|---|
| `OwlBankData` | Encryption keys, DynamoDB tables, secrets, alarm topic, Access Analyzer. |
| `OwlBankNetwork` | The VPC for the bridge (Fargate, or the AgentCore Runtime in VPC mode). |
| `OwlBankAgent` | AgentCore Memory and Gateway. |
| `OwlBankBridgeImage` | The ECR repository for the bridge image. |
| `OwlBankBridge` | The bridge: ECS Fargate behind the ALB, or an AgentCore Runtime. |
| `OwlBankCompute` | The Lambdas: front door, auth service, tools, Context API, Flex authorizer. |
| `OwlBankApi` | The REST API for Twilio's webhooks and the Flex Context API. |
| `OwlBankAdmin` | Optional admin console (`adminConsole`). |

**OwlBankData**

- The CMK (`alias/owlbank-data`, rotation on) for DynamoDB, Secrets Manager, logs, the alarm topic and AgentCore; its CloudWatch Logs statement covers only `/owlbank/*` and `aws-waf-logs-owlbank-*`.
- The token-sealing key (`alias/owlbank-token-sealing`), whose key policy lets only the front door role (encrypt, decrypt), the auth service role (encrypt: it seals the prepared welcome) and the bridge task role (decrypt) use it, with a `call_sid` encryption context, and denies crypto to every other principal; the account root keeps key administration only.
- The alarm topic `owlbank-<stage>-alarms` (CMK, TLS only).
- An IAM Access Analyzer (`owlbank-<stage>-account`, type ACCOUNT).
- An EventBridge rule on the default bus, `owlbank-<stage>-bedrock-logging-change`, that sends CloudTrail's `PutModelInvocationLoggingConfiguration` (this Region only) to the alarm topic; the topic and key policies admit EventBridge only with that rule as the source (production guide, "Bedrock model-invocation logging").
- DynamoDB tables with the key schemas from `owlbank.store.SCHEMAS`, PITR (point-in-time recovery) on, and TTL `expires_at` on tokens, calls and segments.
- Secrets: `owlbank/twilio/api-key` and `owlbank/twilio/auth-token` (placeholders you fill in), `owlbank/twilio/basic-auth` (generated), and `owlbank/twilio/context-api-key` (when `contextApiRestrictedKey=on`).

**OwlBankNetwork**

- A VPC across 2 explicit AZs (`<region>a` and `b`, or `availabilityZones`), with public subnets (ALB, NAT) and private subnets (Fargate, or the Runtime in `agentcore` VPC mode), NAT gateways (`natGateways`, default 1), REJECT flow logs (`/owlbank/vpc/flow-logs`) and a DynamoDB gateway endpoint on the private route tables.
- Not in the app with `bridgeHosting=agentcore` + `agentcoreNetworkMode=public`.

**OwlBankAgent**

- `CfnMemory` with no strategies, a 3-day expiry and the CMK.
- `CfnGateway` (IAM inbound, MCP, CMK); its `level0_tools` Lambda target is added by `OwlBankCompute`.
- Its outputs `GatewayUrl` and `MemoryId` go to the bridge, whose Strands agent loop uses both.
- There is no agent runtime in this stack: the agent loop runs in the bridge.

**OwlBankBridgeImage**

- The bridge image's ECR repository `owlbank-<stage>-bridge` (immutable tags, scan on push, the CMK by its alias, `RETAIN`).
- In the app on both hostings.
- It follows Data for deploy order only, and with `agentcore` the Bridge stack follows it.

**OwlBankBridge**

- ECS Fargate for `src/tac_bridge` (image from its Dockerfile, repo-root context, arm64, port 8080), tasks in private subnets that accept traffic only from the ALB, egress on 443 only.
- The ALB (see the two modes above) has access logs (private S3, SSE-S3), the 900 s idle timeout and health check `/health`.
- In CloudFront mode the stack also holds the distribution (`PriceClass_100`, HTTP/1.1 only, HTTPS viewers only, caching disabled, all HTTP methods, an origin request policy that forwards all viewer headers and query strings and no cookies), the VPC origin (HTTP only, read and keep-alive timeouts from context) and the CLOUDFRONT-scope web ACL. In CloudFront mode the internal ALB's HTTP listener returns a fixed 403 unless the request carries the secret `X-Origin-Verify` header (above).
- Twilio credentials arrive as task-definition `secrets`.
- The task role has the fixed name `owlbank-<stage>-bridge-task`.
- WAF logs go to `aws-waf-logs-owlbank-<stage>-alb` (custom domain) or `-cloudfront` (CloudFront mode), with `authorization`, `cookie`, `x-twilio-signature` and the query string redacted: the query carries the WebSocket nonce.
- The web ACL allows only `GET /ws` and `POST /webhook` (not `/health`: the ALB's health checks never pass the WAF).
- Alarms: ALB and target 5XX, UnHealthyHostCount, RunningTaskCount below `bridgeDesiredCount`, WAF BlockedRequests spike, CloudFront 5xx error rate above 5% (CloudFront mode), and TAC's WebSocket signature-failure log lines.
- **With `bridgeHosting=agentcore`** the stack holds none of the ECS, ALB, CloudFront or WAF resources: instead the Runtime, its execution role (same construct ID `TaskRole` and fixed name `owlbank-<stage>-bridge-task`, with a `bedrock-agentcore.amazonaws.com` trust, so the token key policy is unchanged), its security group (VPC mode), its log group, the presign role, the relay parameter (the Runtime ARN) and the dormant retained resources (above).

**OwlBankCompute**

- Six Lambdas (`frontdoor`, `auth_service`, `bank_tools`, `level0_tools`, `context_api`, `flex_authorizer`), plus `runtime_warmer`, `model_poller`, `conversation_sweep` and `recap_writer` when their features are on, Python 3.12 arm64, each with its own role and a CMK-encrypted log group.
- The front door and auth service roles have the fixed names `owlbank-<stage>-frontdoor` and `owlbank-<stage>-auth-service` (the token key policy names them); the auth service role gets `kms:Encrypt` on the token key only (`WelcomeSealing`, with the `call_sid` condition).
- Errors and Throttles alarms per function, a metric filter plus alarm on the front door's `security: rejected request` log line, and one on its `slot_mode_invalid` line (`SlotModeInvalid`, 1 in 5 minutes).
- Each role reads and writes only the tables its handler uses (`ACCESS` in `compute_stack.py`; `context_api` reads `calls`, `segments`, `policy` and `catalog`, the catalog for the text the Flex screen pop withholds), and every role that reads the catalog also gets `CatalogScan`, `dynamodb:Scan` on the catalog table only (no index), because the catalog reloads with one paginated Scan (the bridge task role too); no new KMS statement.
- The front door gets `OWLBANK_SLOT_MODE_CEILING`, `OWLBANK_RESOLVER_MODEL_ID`, `OWLBANK_SPEECH_LOG` and `OWLBANK_SPEECH_LOG_REDACTION`, and its role a `SlotResolver` statement (`bedrock:InvokeModel` on the inference profile and its models) only when `slotModeCeiling` isn't `deterministic`.
- The bundle is `owlbank/`, `lambdas/`, `scripts/hash_tool.py` and `data/faq.json`, staged into `build/lambda-src`.
- A dependency layer comes from `build/lambda-deps`.
- `bank_tools` and `level0_tools` have the fixed names `owlbank-<stage>-bank-tools` and `owlbank-<stage>-level0-tools`, so the Agent and Bridge stacks name them by ARN without a stack reference.
- The front door reads the relay host at start-up from the Bridge stack's SSM String parameter `/owlbank/<stage>/bridge/relay` (`OWLBANK_RELAY_PARAMETER`; `ssm:GetParameter` on that parameter only) and builds `wss://<relay host>/ws`, where the host is the Bridge stack's distribution domain (CloudFront mode) or `relay.<domain>`; with `bridgeHosting=agentcore` the parameter holds the Runtime ARN, and Compute adds the `runtime_warmer` Lambda.
- No export connects Bridge and Compute.
- The Gateway's `level0_tools` target is created here (it needs the function to exist).
- With `agentcore` the front door also gets `sts:AssumeRole` on the presign role, `lambda:InvokeFunction` on the warmer and `bedrock-agentcore:StopRuntimeSession` on the Runtime, and the warmer gets `InvokeAgentRuntime` only, plus an alarm on the warmer's `runtime_prewarm_failed` lines with a throttling or quota code.

**OwlBankApi**

- A REST API with WAF and stage throttling: `POST /voice/{incoming,language,factor,connect-action,status,partial,enqueue-action}` goes to `frontdoor` (`partial` is the Gather `partialResultCallback` for early digits, answered 204; `enqueue-action` is the `<Enqueue>` `action`), and `GET /context/{journal_ref}` goes to `context_api` behind the `flex_authorizer` REQUEST authorizer (`X-Flex-Token`, no result cache: every request is validated).
- `OwlBankApi` deploys after `OwlBankCompute`: it invokes the front door's `live` alias.
- `OPTIONS` goes to the Lambda without the authorizer.
- With `domainName`, the API runs on `voice.<domain>` and `execute-api` is turned off; without it, the default `execute-api` endpoint stays on (`https://<id>.execute-api.<region>.amazonaws.com/v1/voice/...`).
- WAF logs go to `aws-waf-logs-owlbank-<stage>-api` (`authorization`, `cookie` and `x-twilio-signature` redacted).
- The web ACL also blocks any `/voice/*` request with no `Authorization` header (`AuthorizationHeaderRequired`: Twilio always sends Basic credentials).
- Alarms: API 5XX and a WAF BlockedRequests spike.

**OwlBankAdmin**

- Optional (`adminConsole`): the admin console; see "The admin console" below.
- A Cognito user pool (admin-created users only, groups `admin`, `admin-editor`, `admin-viewer`, managed login with authorization code + PKCE, TOTP MFA at `prod`), the site (private S3 bucket, CloudFront with origin access control, CSP/HSTS headers, CLOUDFRONT web ACL), the `admin_audit` table (CMK, TTL), the admin API (regional REST API, Cognito authorizer and a Lambda proxy on every route, regional web ACL) and its Lambda `lambdas.admin_api` (role: `GetItem`/`Query`/`PutItem` on the policy, catalog and audit tables only, plus `PolicyBatchRead` (`dynamodb:BatchGetItem` on the policy table) and `CatalogScan` (`dynamodb:Scan` on the catalog table) for the cache reloads, and the user-management actions on the one pool).
- The API is served from the console's own CloudFront domain under `/api/*`, so there is no CORS. Nothing in the call path depends on it.

## Context parameters

| Key | Default | Meaning |
|---|---|---|
| `accountId` | `111111111111` (fake) | Target account |
| `region` | `us-east-1` | Target region |
| `stage` | `dev` | `dev`, `test` or `prod`. `developerPhone` and `testNumbers` are rejected in `prod`. `prod` also retains log groups (1-year retention) and turns on DynamoDB and ALB deletion protection. The stage is in the fixed role, web ACL, log group, topic and analyzer names |
| `domainName` | unset | Unset: the **CloudFront mode** (requires `region` `us-east-1`, and `stage` `dev` or `test`: `stage=prod` without a domain fails synth). Set: the custom-domain mode, with the API on `voice.<domain>` and the bridge on `relay.<domain>`, and `execute-api` off. Requires `certificateArn` |
| `certificateArn` | unset | ACM certificate for the API domain and the ALB, in the custom-domain mode (required there, ignored otherwise) |
| `developerPhone`, `testNumbers` | unset | Owned numbers in E.164 form (for example `+14155550123`), published as the `SeedOwnedNumbers` output for `scripts/seed.py`, in dev and test only |
| `bridgeDesiredCount` | `1` | Number of Fargate tasks. Default for a first deployment; production runs 2 or more across AZs. Keep it at `1` in the first-deploy order below (the secrets are real and the configuration ID exists before the bridge starts). Use `0` only to deploy the Bridge stack before the secrets are written (its tasks cannot start on the placeholder secrets and the deploy would roll back), then redeploy with `1` |
| `modelIds` | the Region's geography profiles of Haiku 5.5, Haiku 4.5 and Sonnet 5.5 (`us.` in `us-east-1`) | The agent's models in preference order, one to three inference-profile IDs, as a JSON list (`-c modelIds='["us.anthropic.claude-haiku-5-5"]'`) or comma-separated. `OWLBANK_MODELS` on the bridge (both hostings): a JSON list of entries with `id`, `thinking`, `max_tokens`, `text_release` and `prompt_caching`. A list of one gives a single model (no failover). Each entry must be the deployment Region's geography profile (`us.` from a US Region) or an explicit `global.` profile, which prints a synth warning: it may be processed in any commercial Region. Another geography's profile, a bare model ID, a repeat, or more than three entries fail synth. The bridge role may invoke exactly the listed entries, each only through its profile. Run `scripts/preflight.py` first: it checks each entry live and prints the `-c modelIds=...` to use |
| `modelParams` | unset | Per-entry overrides as a JSON object keyed by a `modelIds` entry: `{"<model id>": {"thinking": ..., "max_tokens": ..., "text_release": ..., "prompt_caching": ...}}`, each field optional. `thinking`: `adaptive`, `off`, `default`, `between_tools` or `enabled:<budget>` (budget at least 1024, below `max_tokens`); `max_tokens` 64 to 8192; `text_release` `stream` or `message`; `prompt_caching` `on` or `off`. `promptCaching` sets every entry and `modelParams` overrides it. An entry starts from its model's known defaults (Haiku 5.5 and Sonnet 5.5: `adaptive` + `stream`; any other model, Haiku 4.5 included: `off` + `message`; 2000 tokens with reasoning, 1000 with `off`), then `promptCaching` (every entry), then this. Example: `-c 'modelParams={"us.anthropic.claude-haiku-5-5":{"thinking":"off","text_release":"message"}}'`. A key not in `modelIds`, an unknown field, `stream` with `off`, or a thinking the model refuses (Haiku 4.5 `adaptive`; Sonnet 5.5 `off`; Haiku 5.5 and Sonnet 5.5 `enabled:`) fails synth naming the entry |
| `failoverTest` | `off` | Test-only latency injection for exercising model failover: a delay in seconds, above 0 and at most 30 (`-c failoverTest=6`), added before the preferred (first) entry's first token. Sets `OWLBANK_FAILOVER_TEST=<seconds>` on the bridge (both hostings) and on the poller, so its recovery pings are delayed too (deploy `OwlBankBridge` and `OwlBankCompute`); unset or `off`, no variable is set. Any value at `stage=prod` fails synth, and so does anything but `off` or a number in range. Remove it after the test (deploy `OwlBankBridge` without it) |
| `modelFailover` | `on` | Model failover on or off. The `modelstats` table in `OwlBankData` is always built, whatever this setting (fixed name `owlbank-<stage>-modelstats`, on demand, the stack's CMK, TTL `expires_at`, no Streams, no point-in-time recovery, no index; retained, and deletion-protected at prod like the other tables), so switching the setting never deletes it. `on` with two or more `modelIds` entries uses it: the table's consumed-write alarm at twice the sampling budget; the `model_poller` Lambda in `OwlBankCompute` (arm64, 128 MB, every minute; it queries the samples, reads and writes the state record, reads the `model_failover` policy section (`OWLBANK_TABLE_POLICY`), and pings and rechecks every listed entry); `OWLBANK_TABLE_MODELSTATS` on the bridge, whose role may update sample items (partition `samples`) and read the state record (partition `state`) only (the partitions are fixed values, not the stage: each stage has its own table); and the alarms (state not refreshed for 3 minutes, every entry degraded or unavailable, `model_unavailable` at once, with its own alarm naming the preferred entry, and `ActiveRank` above 0 for 15 minutes). `off`, or a list of one, deploys the single-model shape: only the first entry reaches IAM and `OWLBANK_MODELS`, and none of the above exists except the empty, unused table. `failoverTest` with `off` or a list of one fails synth. Turning it on or off is a deploy of `OwlBankData`, `OwlBankCompute` and `OwlBankBridge` (`--all` order is fine: the table is named by its fixed name, not exported, and a bridge without the table falls back to its in-process view of model health). ## The admin console (`OwlBankAdmin`)

**Deploy order.** After `OwlBankData` (it reads the policy and catalog tables and the CMK by cross-stack reference) and `OwlBankApi` (which owns the account-level API Gateway CloudWatch role the admin stage logs with); `app_builder` declares both. The tables must be seeded ("First deploy", step 9) or the console's API answers 503 `not_seeded`. Group 3 of "First deploy" already deploys the console in `dev` and `test`; this command deploys it alone. From `infra`, with the flags written inline (the context rule):
```
npx aws-cdk@2 deploy OwlBankAdmin --exclusively \
  -c accountId=$(aws sts get-caller-identity --query Account --output text --profile <profile>) \
  -c adminEmail=<email> \
  -c twilioPhoneNumber=+1... \
  <the hosting context> \
  --outputs-file cdk-outputs-admin.json
```
`--exclusively` deploys only `OwlBankAdmin`, but synth still builds every stack, so pass the same `-c` values as the live stacks, the hosting context included (on `agentcore`, `-c bridgeHosting=agentcore -c bridgeImageDigest=sha256:<current digest>`; on Fargate, nothing). Use an outputs file of its own: `--outputs-file` writes only the stacks in that deploy, and the seed reads `cdk-outputs.json`. The first deploy of `OwlBankAdmin` creates IAM roles, so it needs a role that can change IAM policies. Pass `-c adminEmail=<email>` on the deploy that first creates `OwlBankAdmin` (it creates the first user). The user resource is retained, so a later deploy without it leaves the user in place (remove users in the console). Use the same value if you pass it again; a different value creates a second admin.

**First sign-in.** Cognito emails the first user (an `admin`) a temporary password, valid 3 days. Open the `ConsoleUrl` output: it goes straight to the managed login page. Sign in with the email and the temporary password, and set a new one (12+ characters, all classes). At `stage=prod` the pool also requires TOTP MFA. More users are added from the console's Users view (admins only); each gets the same email. Without `adminEmail` no user exists: redeploy with `-c adminEmail=...` (no other way to create the first user is provided).

**How it fits together.** `/` and the static files come from the private site bucket; `/api/*` goes to the admin REST API's regional endpoint with origin path `/v1`, so `/api/tools` is the API resource `/api/tools` (the handler strips `/api`). That behavior has caching off in effect (the cache policy keys on `Authorization` so CloudFront forwards it, max TTL 1 s, and the API sends `no-store`), forwards `Content-Type` and the query string, never cookies. CloudFront adds `X-Origin-Verify` from the generated secret `owlbank/<stage>/admin/origin-verify` (a dynamic reference, never in the template), and the API's web ACL blocks any request whose header doesn't match (`OriginVerifyHeaderRequired`), so the `execute-api` URL is unusable directly. The site's `config.js` (pool, client, login domain, redirect URI, API base `/api`, and the stage, which the sidebar shows as a badge: amber for `dev` and `test`, red for `prod`) is generated at deploy and uploaded with the files by `SiteDeployment`, which also invalidates the distribution. Tokens stay in the page's memory; a reload signs in again through Cognito's session.

**Two deployments for the site.** `SiteDeployment` uploads `src/admin_console/` without `tests/`, `package.json`, `*.md` and `fonts/*.woff2` (`SITE_EXCLUDE`); the handler sets each file's type from its extension (`.svg` is `image/svg+xml`, `fonts/OFL.txt` is `text/plain`). `FontDeployment` uploads `fonts/*.woff2` to `fonts/` with `Content-Type: font/woff2` (the handler's MIME table may not know `.woff2`) and `Cache-Control: public, max-age=31536000, immutable`, which is safe because the file name carries the version (`Inter-4.1-latin-var.woff2`). Both prune, and neither deletes the other's files: `SiteDeployment` excludes `fonts/*.woff2` from its prune too, and `FontDeployment` prunes only under `fonts/` and skips `*.txt`. Both share CDK's one handler, log group and memory. The site WAF's static-file rule (`SITE_FILES`) allows `.woff2` alongside `html`, `js`, `css`, `svg`, `png`, `ico` and `txt`. The CSP is unchanged: the font, the icon sprite (`icons.svg`) and the owl mark (`owl.svg`) all come from the console's own origin.

**The font.** Inter 4.1 (rsms/inter), one variable WOFF2 instanced to weights 400 to 700 and subset to Latin-1 plus common punctuation (Spanish included), about 28 KB. Its license, the SIL Open Font License 1.1, ships next to it as `fonts/OFL.txt` and is served with the site. Where it came from, the checksums and the commands that reproduce it byte for byte are in `src/admin_console/fonts/README.md` (not deployed). If the font fails to load, the console uses the system sans-serif (`font-display: swap`).

**Sign-in behavior.** A signed-out visitor goes straight to the managed login page, with no page of the console's own in between, and comes back to the view they asked for (the hash route travels in the PKCE record in `sessionStorage`, checked by `safeHash` both ways). The console never redirects by itself after a failure:
- a sign-in error (an `error` in the callback, a state mismatch, a failed token exchange, an unreachable login service, or a browser that blocks `sessionStorage`) shows an error page with the reason, the code and **Try again**;
- a loop guard (`owlbank-admin-signin-guard` in `sessionStorage`) counts automatic redirects not followed by a successful sign-in; the third within 120 s is refused and shows "Sign-in didn't complete". A successful sign-in or Try again resets it;
- a session that ends mid-use (the refresh fails) shows "Your session has ended" with **Sign in again**, so unsaved edits aren't thrown away and a 401 can't loop.

Sign-out revokes the refresh token and ends the Cognito session, so the next visit shows the login form rather than signing the user straight back in.

**What to check on the first deploy** (the parts synth can't prove):
- The `/api/*` origin header and the WAF rule resolve the dynamic reference: `GET <ConsoleUrl>api/tools` without a token is API Gateway's 401 (it got through the WAF), and `GET https://<api-id>.execute-api.us-east-1.amazonaws.com/v1/api/tools` is the WAF's 403.
- CloudFront forwards `Authorization`: signed in, the Tools view loads.
- Managed login: sign-in, token exchange, refresh after an hour and sign-out all work.
- The site WAF (count mode in dev) logs no would-block for the console's own requests; read its log group `aws-waf-logs-owlbank-<stage>-admin-site` before switching `wafManagedRuleMode` to `block`.
- Users: creating a user sends the invitation email; a viewer gets 403 on a save.
- The site's types: `curl -I` on `<ConsoleUrl>fonts/Inter-4.1-latin-var.woff2` gives `font/woff2` and `immutable`, on `icons.svg` `image/svg+xml`, on `fonts/OFL.txt` `text/plain`, and on `theme.js` a JavaScript type; each carries the same CSP header.
- After a later deploy that changes the site's files (the main deployment then prunes), `fonts/Inter-4.1-latin-var.woff2` and `fonts/OFL.txt` are still served.

**Rotating the origin-verify secret.** Write a new version of `owlbank/<stage>/admin/origin-verify`, then deploy `OwlBankAdmin -c adminOriginVerifySecretVersion=<version id>`: the distribution and the web ACL change in one update (a few minutes of 403s while CloudFront propagates).

**Removing it.** `npx aws-cdk@2 destroy OwlBankAdmin` removes the console without touching calls; in `dev` and `test` the pool, audit table, bucket and secret go with it (in `prod` they are retained).

## cdk-nag

AwsSolutions runs on every synth, and a finding without an acknowledgement fails synth. IAM5 wildcards are avoided with explicit grants (`owlbank_infra/grants.py`) rather than suppressed. These acknowledgements remain, each with its reason in the code:

| Rule | Where | Why |
|---|---|---|
| APIG4, COG4 | `POST /voice/*` | Twilio can't send SigV4, and a REST authorizer can't see the signed body. The handler checks `X-Twilio-Signature` and Basic credentials first, behind WAF and throttling |
| COG4 | `GET /context/*` | Flex users aren't Cognito users. The Flex token authorizer is used instead |
| APIG4, COG4 | `OPTIONS /context/*` | A CORS preflight can't carry the token. It returns no data |
| IAM4 | API Gateway's CloudWatch role | The AWS-documented managed policy for API Gateway account logging |
| IAM5 `Resource::*` | Lambda roles | X-Ray `PutTraceSegments` and `PutTelemetryRecords` have no resource-level permissions. On the front door also `comprehend:DetectPiiEntities` (the PII redactor), which has none either |
| IAM5 `Resource::*` | Bridge task role | `comprehend:DetectPiiEntities` has no resource-level permissions |
| IAM5 `bedrock:*::foundation-model/<model>` | Front door role and bridge task role | One specific model in any Region, only through the deployment's geography inference profile (`bedrock:InferenceProfileArn` condition). The profile picks the Region; direct invocation stays denied everywhere |
| IAM5 `Resource::*` | ECS execution role | `ecr:GetAuthorizationToken` has no resource-level permissions |
| IAM5 log-stream `:*` | Lambda roles | Log streams under the function's own log group are named at runtime |
| L1 | Lambdas | Python 3.12 is pinned |
| SMG4 | Secrets | Twilio credentials are rotated in Twilio, then written by the script. The generated origin-verify header secret is rotated by a new version plus `originVerifySecretVersion`, because the distribution and the ALB rule must change together |
| ECS2 | Task definition | The environment holds only non-secret configuration. Credentials are `secrets` |
| AwsSolutions-EC23 | ALB security group (custom-domain mode) | 443 has to be open: Twilio uses dynamic IPs, and the solution does not use Twilio Static Proxy |
| CFR1 | Distribution (CloudFront mode) | No geo restriction: Twilio connects from its own regions, not the caller's country, so an allow-list risks blocking Twilio. The CloudFront web ACL, the Twilio signature and the nonce protect the endpoint |
| CFR3 | Distribution (CloudFront mode) | Standard logging needs an ACL-enabled S3 bucket, which this solution does not use (no S3 ACLs). The web ACL logs every request (redacted) to a CMK-encrypted log group, and the ALB writes access logs |
| CFR4 | Distribution (CloudFront mode) | The default `*.cloudfront.net` certificate fixes the minimum TLS version (TLSv1); a stricter policy needs a custom domain. The trade-off of the CloudFront mode |
| AwsSolutions-S1 | ALB log bucket | It is the log bucket |

No Allow statement anywhere has a `*` principal, `NotPrincipal` or `NotAction` (`infra/tests/test_aws_defaults.py`). A **Deny** with `*` is allowed only if it is on the test's named allow-list, since a Deny for everyone can only be written with `*` and grants nothing:

- The TLS-only Deny (`aws:SecureTransport=false`) on the ALB log bucket and the alarm topic.
- The token key's crypto Deny (`ArnNotEquals aws:PrincipalArn` the three sealing roles), on that key only.

The tests also fail on a policy hidden in a JSON string, a Lambda permission without `SourceArn`, any bucket other than the ALB log bucket, a bucket-policy Allow to anything but the log-delivery principals, a new policy-bearing resource type, and a `Resource: "*"` statement with an action that has resource-level permissions.

The ALB log bucket's log-delivery statements carry `aws:SourceAccount`, except the one for the regional ELB account (the account ID is in AWS's "Enable access logs" documentation for your Region), a cross-account principal that sends no source account; it is limited to `s3:PutObject` under `alb/AWSLogs/<account>/`.

## Twilio secrets: the manual step

Three secrets (and a fourth for the Context API's restricted key), all in Secrets Manager under the customer-managed key, created by `OwlBankData`:

| Secret | Created and filled by | Read by |
|---|---|---|
| `owlbank/twilio/basic-auth` | CDK creates it; **Secrets Manager generates** `{"user": "owlbank", "password": "<48 hex>"}` at first deploy (user = context `basicAuthUser`). No one sets or sees it | Front door (checking incoming webhooks; 60 s cache, and a failed check forces one re-read); `twilio_setup.py --phase post`, which puts it in the webhook URLs. Not the bridge. Optionally holds the previous password during a rotation overlap (below) |
| `owlbank/twilio/api-key` | CDK creates a placeholder; **you write** the value after the Data stack | Front door, `auth_service` and `flex_authorizer` (300 s cache; Flex token validation needs a Standard key); `recap_writer`, and `conversation_sweep` (Flex only); the bridge (at start); `context_api` only with `contextApiRestrictedKey=off`; `twilio_setup.py`, `memory_history.py`, `web_activity.py` |
| `owlbank/twilio/auth-token` | CDK creates a placeholder; **you write** the value after the Data stack | Front door (checking `X-Twilio-Signature`; 300 s cache); the bridge (at start: signature checks on `/webhook`) |
| `owlbank/twilio/context-api-key` | Created empty by `OwlBankData` when `contextApiRestrictedKey=on` (the default); `twilio_setup.py --phase pre` writes a Twilio Restricted key into it | `context_api` only (300 s cache) |

**Where the values come from (Twilio Console).** Create a **Standard API key** under Account, API keys & tokens; the Console shows the key SID (`SK` + 32 hex) and its secret once. The `account_sid` is the SID of the account the blueprint runs in (`AC` + 32 hex; use a dedicated subaccount, see the production guide). The **Auth Token** is on the same page, under the account's live credentials. **A Standard key can't read the Accounts resource or create keys** (the Accounts read fails with error 70004), so `twilio_setup.py` reads the Auth Token secret for those two requests (in every phase) and uses the key for the rest; the front door's warm-up reads a resource a Standard key can read.

**JSON shapes** (`src/owlbank/secret_schema.py` is the one definition; `check_secrets.py` checks it):

```json
{"account_sid": "AC<32 hex>", "api_key": "SK<32 hex>", "api_secret": "<32 letters or digits>"}
```

for `owlbank/twilio/api-key`, and

```json
{"auth_token": "<32 hex>"}
```

for `owlbank/twilio/auth-token`.

**Three ways to write them.**

1. **Console.** Secrets Manager, Secrets, the secret, Retrieve secret value, Edit, Plaintext: paste the JSON, Save.
2. **CLI, from a file** (never inline: a value on the command line lands in shell history and in the process list). Create the file with `umask 077`, in an editor, then delete it:

   ```bash
   aws secretsmanager put-secret-value --secret-id owlbank/twilio/auth-token \
     --secret-string file://auth-token.json --profile <profile>
   ```

3. **`scripts/populate_secrets.py`** (optional helper that validates before it writes and refuses a secret that is not under the customer-managed key). Dry run is the default; `--apply` writes. With no other option it asks for each value with no echo (`getpass`); `--only twilio_api_key` or `--only twilio_auth_token` (repeatable) asks for one. `--from-file PATH` reads `{"twilio_api_key": {...}, "twilio_auth_token": {...}}` instead and refuses a file that is readable by group or others (`chmod 600`); a missing entry is skipped. Neither mode prints a value.

   ```bash
   uv run python scripts/populate_secrets.py --cdk-outputs infra/cdk-outputs.json --apply
   uv run python scripts/populate_secrets.py --cdk-outputs infra/cdk-outputs.json --from-file twilio-secrets.json --apply
   ```

Then `uv run python scripts/check_secrets.py --cdk-outputs infra/cdk-outputs.json`: read-only; for each secret it reports set or placeholder, well formed or the field at fault, and the key type; exit 0 only if every secret it checks passes (a `PENDING` `context_api_key` is allowed unless `--strict`). It never prints a value.

**Your own pipeline** (for example a vault sync) may write the two Twilio secrets instead. Its role needs `secretsmanager:PutSecretValue` on those two ARNs, and `kms:GenerateDataKey` and `kms:Decrypt` on the stack's CMK with the condition `kms:ViaService` = `secretsmanager.<region>.amazonaws.com`. Secrets Manager calls `GenerateDataKey` on the caller's behalf for every new value, and `Decrypt` when a `PutSecretValue` repeats an existing version (a retry with the same client request token), to check that the value is the same. It never calls `kms:Encrypt` for `PutSecretValue`, so don't grant it ("Secret encryption and decryption" in the Secrets Manager User Guide). Keep writers to that list: CloudTrail records every `PutSecretValue` (and `GetSecretValue`) with the caller, so a change is attributable.

**When a new value takes effect.** The Lambdas read at runtime through `owlbank.secrets` and cache for 300 s, so a new value is in use at most 300 s after the write. The bridge reads only at start: on Fargate ECS injects the two Twilio secrets into the task as task-definition `secrets` when the task starts, so running tasks keep the old values until they are replaced; on `bridgeHosting=agentcore` each call's Runtime session reads them by ARN when it starts, so new calls get the new values and calls already in progress keep the old ones.

To replace the Fargate bridge's tasks with ones that read the current values (rolling: the new task starts and passes its health check before the old one drains; if the new task can't start with the new value, the circuit breaker rolls back and the old task keeps serving):

```bash
aws ecs list-clusters --profile <profile>
aws ecs list-services --cluster <cluster> --profile <profile>
aws ecs update-service --cluster <cluster> --service <service> --force-new-deployment --profile <profile>
aws ecs wait services-stable --cluster <cluster> --services <service> --profile <profile>
```

On `agentcore` there is nothing to restart: wait until the calls that started before the write have ended.

**Rotation.** Managed Secrets Manager rotation doesn't cover third-party keys, so these are manual. Do them in a quiet period.

1. *Twilio API key.* Create a new key in Twilio, write it with `populate_secrets.py --only twilio_api_key --apply` (or any way above), run `check_secrets.py`, force a new deployment of the bridge service (above) and wait until it is stable, make a test call, and only then, at least 300 s after the write, revoke the old key in Twilio. Revoking earlier breaks the running bridge task and the Lambdas' cached copy.
2. *Auth Token.* In Twilio, create a secondary token and promote it (the secondary-token flow), then at once write the new token the same way and force a new deployment of the bridge service. Twilio signs with the new token from the promotion, so signature checks fail until the write reaches the front door (up to the 300 s cache) and the new bridge task is in service. Do the steps back to back.
3. *Basic auth* (no downtime). The front door accepts the current password and, for an overlap after a rotation, the previous one; the Twilio signature check then uses the password that matched, because Twilio signed the URL it held. Order matters:
   1. `uv run python scripts/populate_secrets.py --cdk-outputs infra/cdk-outputs.json --new-basic-password --apply` writes a new generated password, keeps the user and keeps the old password as the previous one for `--overlap-hours` (default 8: 2 to apply, 4 for the longest call, 2 margin), counted from the write. It prints the deadline by which step 3 must run. Neither password is echoed.
   2. Wait 60 s (the secret's cache lifetime). A callback that reaches an instance whose cache predates the write can be refused for at most that long.
   3. Run `uv run python scripts/twilio_setup.py --phase post --account-sid AC... --phone-number <twilio-number> --cdk-outputs infra/cdk-outputs.json --apply` so the number's webhooks, the Orchestrator callbacks and, with Flex, the TaskRouter callbacks carry the new password. With Flex, add `--with-flex --taskrouter-events` to this command: otherwise TaskRouter's event callback URL keeps the old password and the events are refused after the overlap. Twilio keeps sending the old one until then, and TwiML already returned to a call in progress carries it.
   4. Optional: end the overlap early with `populate_secrets.py --cdk-outputs infra/cdk-outputs.json --clear-previous-basic-password --apply` (the previous password stays accepted for up to 60 s more). The `twilio_basic_previous_accepted` log line (call-keyed, no password) shows when it is no longer in use; `check_secrets.py` reports an active previous password and its deadline.
   **Don't rotate twice inside one overlap.** The script warns but doesn't stop you: the second rotation drops the oldest password (at most two are ever accepted), so calls started before the first rotation can then lose callbacks. Finish `post --apply` first, or wait for the overlap to end. The bridge doesn't read this secret, so no bridge deployment is needed. Rotate after a screenshot or screen share that showed a webhook URL.

## First deploy

Run every `cdk` command with a deploy role: CDK deploy needs `iam:PassRole` on the CloudFormation execution role, and creating the IAM roles needs more than a power-user role. The order matters, and the reasons are in the paragraph that follows. The flags follow the context rule ("Conventions"). Step 7 has a Twilio-side prerequisite (the AI/ML Features Addendum); the root README lists the prerequisites under [Set up your Twilio account](../README.md#set-up-your-twilio-account).

**Why this order.** The bridge container calls Twilio at startup, so it needs real secret values (a task whose secret is still the generated placeholder cannot start: the JSON key is missing, the service rolls back, and the deploy fails) and the Twilio Conversation Configuration ID (`TWILIO_CONVERSATION_CONFIGURATION_ID`). But the webhooks need the API and relay domains, which exist only after the deploy. So Twilio setup is split (`twilio_setup.py --phase pre|post`) around the deploy, and the secrets are written after `OwlBankData` and before every stack that reads them. Phase pre needs the Twilio API key, so it runs after the secrets are written.

1. **AWS credentials.** Sign in the way your organization does (an assumed role, an IAM Identity Center profile or credentials in the environment), then verify with `aws sts get-caller-identity`. Every later command uses these credentials.
2. **Context.** Pass the account on the command line, never in a file: `-c accountId=$(aws sts get-caller-identity --query Account --output text)`. In `infra/cdk.json` set `region` (`us-east-1` without a domain); leave `modelIds` unset unless preflight says otherwise (`cdk.json` has none; step 3); `stage` is `dev` there. Keep phone numbers out of repository files and pass the Twilio number (E.164) on every deploy that includes `OwlBankBridge`: `-c twilioPhoneNumber=+1...`. Without it, on Fargate the bridge's tasks fail at start-up (`KeyError: 'TWILIO_PHONE_NUMBER'`) and the ECS circuit breaker rolls the deploy back (running tasks keep serving); with `bridgeHosting=agentcore` synth fails. Leave `bridgeDesiredCount` at `1`. Custom-domain mode only: also `domainName` and `certificateArn` (ACM, in the region). Leave `wafManagedRuleMode` unset (`count` in `dev`). To set the first console user, add `-c adminEmail=<email>` (optional; used in step 10; pass the same value every time, or leave it out once the first user exists). **If an organization SCP denies `s3:PutBucketPublicAccessBlock`** (the bootstrap in step 5 fails with AccessDenied on that action), `-c s3PublicAccessBlockMode=account` is required on every deploy, and step 5's bootstrap needs `--public-access-block-configuration false` (see the row in "Context parameters"); leave both out otherwise. Context flags are not remembered between deploys: every `cdk` command in this guide carries the full set (`accountId`, `twilioPhoneNumber` where `OwlBankBridge` is in the deploy, `adminEmail`, `s3PublicAccessBlockMode`, and any other `-c` you use).
3. **Preflight (read-only).** `infra`: `uv run python scripts/preflight.py --profile <profile> --stage dev --slot-mode-ceiling <ceiling>` (`<ceiling>` is the `slotModeCeiling` you deploy; `assisted` by default). Model access must be on first: Console, **Bedrock**, **Model access** (Anthropic models ask once for a use-case form) for Claude Haiku 5.5, Claude Haiku 4.5 and Claude Sonnet 5.5, the default list, and the resolver's `us.anthropic.claude-haiku-5-5`; the preflight sends a one-token test request to each. If it prints `deploy with: -c modelIds=[...]` and the list differs from the default, add `"modelIds"` to `infra/cdk.json` or pass it on every Bridge and Compute deploy. It checks:
   - account-level S3 Block Public Access (a FAIL here, like the CloudTrail WARN below, concerns a setting that may belong to someone else: ask the account owner and do not change account-wide settings in a shared account; `s3PublicAccessBlockMode=account` is for an SCP that denies the per-bucket setting and relies on this account-level one);
   - the inference profile's Regions and model access;
   - Bedrock model-invocation logging (FAIL if it delivers text in the deployment Region, whose setting applies wherever the `us.` profile runs the call; only a WARN with `--slot-mode-ceiling deterministic`, or with `--accept-text-logging` in dev or test);
   - a CloudTrail trail that logs management write events in the Region (WARN in `dev` and `test`, FAIL at `--stage prod`; the logging alarm needs it);
   - in CloudFront mode, that `cloudFrontOriginPrefixListId` is this Region's `com.amazonaws.global.cloudfront.origin-facing` list (`--prefix-list-id` if you changed the key, or `--no-prefix-list` in the custom-domain mode);
   - from the repository files only, that every model in the list to deploy has a validated system prompt in each catalog language (`data/prompt_validation.json`; pass `--model-params` as you deploy; prompt caching is not a validated parameter);
   - from the repository files only (the "Agent prompt texts" preflight check), that no published `agent.*` text breaks the placeholder allow-list (`agent.system.*`, the web-activity blocks and the unverified caller context have none; `agent.caller_context` has exactly `{firstName}`, `{memory}`, `{profile}`) and that every catalog language has both caller-context frames (the seed refuses the same).

   It prints the fix command for anything that fails.
4. **Build the Lambda layer and set up a container client.** `infra`: `uv run python scripts/build_lambda_deps.py`; it worked when `infra/build/lambda-deps/python/twilio/` exists (without it the layer ships empty and the Lambdas fail at run time importing `twilio`). The CDK deploy builds the bridge image (step 10) with a container client. This guide uses Finch on macOS (AWS's open-source container client); elsewhere Docker works, with `CDK_DOCKER` unset. For Finch: `brew install finch`, `finch vm init`, then in the shell that runs `cdk deploy` set `export CDK_DOCKER=finch` (and, only if the build can't find the engine, `export DOCKER_HOST=unix:///Applications/Finch/lima/data/finch/sock/finch.sock`). Everything here is arm64 (Fargate, the Lambdas and an Apple Silicon Mac), so on an arm64 build host no emulation is involved. The bridge image is `linux/arm64`: on an Intel Mac or x86 Linux use Docker with buildx and install the emulation once with `docker run --privileged --rm tonistiigi/binfmt --install arm64`; the build is then slower. A local build works: `finch build --platform linux/arm64 -f src/tac_bridge/Dockerfile -t owlbank-tac-bridge:local .` from the repository root.
5. **Bootstrap and deploy the Data stack first.**
   - **5a. Bootstrap.** `infra`: `npx aws-cdk@2 bootstrap aws://$(aws sts get-caller-identity --query Account --output text)/<region> -c twilioOutputs=`, where `<region>` is `us-east-1` unless you set `domainName` (then the Region in `infra/cdk.json`, as in step 2). `npx` asks once to install the CLI package: answer `y`. If the SCP case in step 2 applies (an organization SCP denies `s3:PutBucketPublicAccessBlock`), add `-c s3PublicAccessBlockMode=account --public-access-block-configuration false`: the bootstrap bucket's own Block Public Access property would otherwise fail to create. If a failed bootstrap left the `CDKToolkit` stack in `ROLLBACK_COMPLETE`, delete that stack in CloudFormation (it holds nothing yet) and run the bootstrap again.
   - **5b. Deploy the Data stack.** `infra`: `npx aws-cdk@2 deploy OwlBankData -c accountId=$(aws sts get-caller-identity --query Account --output text) -c twilioOutputs= --outputs-file cdk-outputs.json` (plus `-c s3PublicAccessBlockMode=account` in the SCP case); it also stops at a `(y/n)` approval prompt. This creates the CMK, the tables and the secrets, and nothing that reads them: `basic_auth` is generated by Secrets Manager (user `owlbank`, or `basicAuthUser`; a 48-character hex password no one sets or sees), and the two Twilio secrets hold a placeholder until step 6. The Data stack uses nothing from `twilioOutputs` until the recap writer turns on (step 10, once the file holds the Memory store), but synth builds the whole app and loads that file first, and `cdk.json` names `twilio.context.json`, which phase pre (step 7) writes: on a fresh clone the bootstrap and the deploy fail with `twilioOutputs file not found`. `-c twilioOutputs=` (empty) loads no file for the command: pass it on every bootstrap and on this deploy, drop it once the file exists, and don't pass it from step 8 on. The Data stack's token key policy changes at step 10, when the recap writer turns on; that is expected.
6. **Write the two Twilio secrets, then check them** (see "Twilio secrets: the manual step" above for where each value comes from, the JSON shapes and the other ways to write them). `repo`: dry run, then `--apply`; the script prompts for each of the four values with no echo, in this order: Account SID, API key SID, API key secret, Auth Token (the prompts read `twilio_api_key account_sid:`, `twilio_api_key api_key:`, `twilio_api_key api_secret:` and `twilio_auth_token auth_token:`), also in the dry run, which validates their format and writes nothing:
   `uv run python scripts/populate_secrets.py --cdk-outputs infra/cdk-outputs.json` (then `--apply`). Then `repo`: `uv run python scripts/check_secrets.py --cdk-outputs infra/cdk-outputs.json`, which must exit 0 (the secrets set, well formed and under the customer-managed key; no value is printed). It lists `context_api_key` as `PENDING`: that key is created by step 7, so this is expected here and doesn't fail the check. Do not go on until it passes.
7. **Twilio setup, phase pre (needs no domain).** Prerequisites:
   - **AI/ML Features Addendum.** The account owner must have accepted Twilio's AI/ML Features Addendum in the Console (Orchestration, Conversation Orchestrator, *Create a Conversation configuration*, tick the checkbox). **Accepting is enough: do not go on to create a configuration in the Console.** The script creates the real one, and one made by hand would carry capture rules that don't suit this flow. Without the acceptance, the Memory Store and Conversation Configuration steps fail with error 20003; wait 1 to 2 minutes after accepting.
   - **No Flex needed.** The default path makes no Flex or TaskRouter call. To add Flex later, see [docs/add-flex.md](../docs/add-flex.md): setup is re-run with `--with-flex` (and `--create-flex` if the account has no Flex yet), and the stacks are redeployed.

    npx aws-cdk@2 deploy OwlBankBridge --exclusively "${flags[@]}" --outputs-file cdk-outputs-2.json

    - WAF can create the log-group resource policy for `aws-waf-logs-*`.

## Deploying `bridgeHosting=agentcore`, and switching back

Run each step against a dev or test account first. Bridge, Compute and Data change IAM roles here (the task role's trust, the presign role, the front door's grants), so they need a role that can change IAM policies (an administrator-level role). Paths: `repo` is the repository root, `infra` is `infra/`.

**Before the first switch on a deployed stack:** the stack must already be deployed on Fargate. Switch in a quiet period: calls in progress during the Bridge and Compute deploys may drop.

**The `-c` values for every command below** (the context rule; none of them is in `cdk.json`, and the account is never stored in a file):

| Value | Why |
|---|---|
| `-c accountId=$(aws sts get-caller-identity --query Account --output text --profile <profile>)` | The target account, read at run time |
| `-c bridgeHosting=agentcore` | The hosting. Leaving it out of a later deploy switches back to Fargate |
| `-c bridgeImageDigest=sha256:<64 hex>` | The image pushed in step 4. Without it, synth of the whole app fails, so it is needed even for a deploy of another stack once `bridgeHosting=agentcore` is passed |
| `-c twilioPhoneNumber=+1...` | Any deploy that includes `OwlBankBridge`, on both hostings (with `bridgeHosting=agentcore` every synth and command needs it): the bridge's TAC configuration needs `TWILIO_PHONE_NUMBER` and the bridge exits at start-up without it. On Fargate the circuit breaker then rolls the deploy back; on `agentcore`, which has no circuit breaker, synth fails without it |
| `-c agentcoreNetworkMode=public` (and at prod `-c agentcoreNetworkModeAck=public-at-prod`), `-c agentcoreIdleTimeoutSeconds=...`, `-c agentcoreSessionQuota=...` | Only if you don't want the defaults |

**Steps.**
1. **AWS credentials.** Sign in the way your organization does (SSO, an assumed role or access keys in the environment), then verify with `aws sts get-caller-identity` (add `--profile <profile>` if you use one). Every later command, and `--profile` where a script takes it, uses these credentials.
2. **Preflight (read-only, except the AZ cache).** `infra`: `uv run python scripts/preflight.py --profile <profile> --stage dev --agentcore` (add `--agentcore-session-quota <n>` if you set `agentcoreSessionQuota`, and `--availability-zones <a>,<b>` if you set `availabilityZones`). It fails if the Region doesn't offer AgentCore Runtime, prints the active-session and new-session-rate quotas next to the sizing rule ("active sessions >= peak concurrent calls + calls in IVR; new-session rate >= peak call arrivals per second"), warns if `agentcoreSessionQuota` differs, caches the AZ map in `infra/cdk.context.json` and checks the VPC's AZ IDs (VPC mode). A FAIL on the AZs: set `availabilityZones` (replaces the VPC) or use `agentcoreNetworkMode=public`.
3. **The image repository.** `OwlBankBridgeImage` is in the app on both hostings, and group 1 of "First deploy" created it; its outputs are in `infra/cdk-outputs.json`.
4. **Build and push the image.** Commit first: a dirty working tree is refused (the tag is `git-<12-hex commit>` and tags are immutable). `repo`: `export CDK_DOCKER=finch` (the script then uses Finch; `--cli docker|finch` overrides), then `uv run python infra/scripts/push_bridge_image.py --outputs infra/cdk-outputs.json --profile <profile>` (dry run: checks the tree, prints the commands), then the same with `--apply`. It builds `src/tac_bridge/Dockerfile` for `linux/arm64`, pushes it, and prints the digest (`sha256:...`). `--repository-uri <uri>` names the repository instead of `--outputs`.
5. **Bridge, Compute and Api, in one command.** `infra`:
   ```
   npx aws-cdk@2 deploy OwlBankBridge OwlBankCompute OwlBankApi \
     -c accountId=$(aws sts get-caller-identity --query Account --output text --profile <profile>) \
     -c bridgeHosting=agentcore -c bridgeImageDigest=sha256:<digest from step 4> \
     -c twilioPhoneNumber=+1... \
     --profile <profile> --outputs-file cdk-outputs-agentcore.json
   ```
   Review `cdk diff` of each stack first (same `-c` values). The CDK also deploys the stacks they depend on: Data (the `RuntimeLogsCmk` key-policy statement for the Runtime log group), Network (unchanged in VPC mode), Agent and BridgeImage (unchanged). Order: Bridge (the Runtime replaces the ECS service, ALB, CloudFront and WAF), then Compute (the front door's agentcore settings and the new `runtime_warmer`; its new environments read the Runtime ARN from the relay parameter), then Api (`POST /voice/orchestrator`). Compute must be in the same deploy: its running environments keep the old relay value until it is deployed (hazards). Wait until the front door's `live` provisioned concurrency is `READY`.
6. **Twilio setup, phase post again: the status callback.** `repo`: `uv run python scripts/twilio_setup.py --phase post --account-sid AC... --phone-number +1... --cdk-outputs infra/cdk-outputs-agentcore.json` (dry run; the plan shows the sink URL as `https://***:***@host/path`), then `--apply`. With the `BridgeHosting` output `agentcore` it points the Conversation Configuration's status callback at `https://<user>:<password>@<api>/voice/orchestrator` (Basic credentials from the `basic_auth` secret, never printed); the number's voice webhook is unchanged.
7. **Post-deploy check and one test call.** `infra`: `uv run python scripts/preflight.py --profile <profile> --stage dev --post-deploy`, then (ceiling not `deterministic`) the live resolver check ("First deploy", step 12). Then one call (runbook, "AgentCore hosting: investigating a call"): a `relay_minted` with `hosting` `agentcore`, a `runtime_prewarm` `ok`, a `ws_session_start` in the Runtime log group, and a `runtime_session_stopped` `ok` at the end.

**Switching back to Fargate (rollback).** One deploy, then the same script. From VPC mode the Bridge stack can't finish its cleanup for hours (step 2 below), so Compute and Api are deployed without waiting for it:
1. `infra`: `export CDK_DOCKER=finch` (the Fargate image is built by the deploy again), then
   ```
   npx aws-cdk@2 deploy OwlBankBridge OwlBankCompute OwlBankApi \
     -c accountId=$(aws sts get-caller-identity --query Account --output text --profile <profile>) \
     -c twilioPhoneNumber=+1... \
     --profile <profile> --outputs-file cdk-outputs-fargate.json
   ```
   (no `bridgeHosting`, which means `fargate`). The Bridge stack recreates the ECS service, ALB and, in the CloudFront mode, a **new distribution with a new `*.cloudfront.net` domain**, and deletes the Runtime (typically about 10 minutes); the dormant retained resources are reused, so nothing fails on "already exists". Compute drops the warmer and the agentcore settings; Api drops `/voice/orchestrator`.
2. **VPC mode: don't wait for the Bridge cleanup.** The Bridge stack then sits in `UPDATE_COMPLETE_CLEANUP_IN_PROGRESS`: the Runtime's security group can't be deleted while AgentCore's `agentic_ai` network interfaces are attached, and AgentCore can hold them for hours (hazards). The command above deploys Compute and Api only after Bridge finishes, so until then the front door still reads the Runtime ARN and every call fails closed (apology, then a human). As soon as the Bridge's Fargate resources exist (its `RelayDomain` output, or the ECS service), deploy the other two from the assembly that command synthesized, in a second terminal, in this order:
   ```
   npx aws-cdk@2 deploy OwlBankCompute --app cdk.out --exclusively --profile <profile> --outputs-file cdk-outputs-compute.json
   npx aws-cdk@2 deploy OwlBankApi --app cdk.out --exclusively --profile <profile>
   ```
   `--app cdk.out` reuses the synthesized templates, so no `-c` values are needed; don't re-synth in between. `--exclusively` skips the Bridge stack that is still cleaning up. Then wait until the front door's `live` provisioned concurrency is `READY`. The first command writes `cdk-outputs-fargate.json` only when it finishes; until then, rollback step 4 takes `--api-domain` and `--relay-domain` (the Bridge stack's new `RelayDomain` output) as well as `--cdk-outputs infra/cdk-outputs.json`, which still supplies the secret ARNs (`SecretBasicAuth` and the others) that `twilio_setup.py` reads. Don't use the agentcore outputs file for this: its `BridgeHosting` would keep the callback on the sink.
3. **Custom-domain mode only:** point `relay.<domain>` at the new `AlbDnsName`.
4. `repo`: `uv run python scripts/twilio_setup.py --phase post ... --cdk-outputs infra/cdk-outputs-fargate.json` (dry run, then `--apply`): the outputs file of this deploy has no `BridgeHosting`, so the status callback goes back to `https://<RelayDomain>/webhook`; it also carries the Data stack's `Secret*` outputs (Data is deployed as a dependency), which the script needs for the Basic credentials (without them: `--secret basic_auth=<ARN> --secret twilio_api_key=<ARN>`, the ARNs from `infra/cdk-outputs.json`). Don't pass the agentcore outputs file here: its `BridgeHosting` would keep the callback on the sink. Twilio can return the old value for a moment after the update, so the read-back re-reads up to four times, 2 s apart, and compares the URLs percent-decoded (Twilio re-encodes Basic credentials in a URL).
5. One test call: `relay_minted` with `hosting` `fargate`, and the bridge lines in `/owlbank/ecs/tac-bridge`.
6. **Later: delete the orphaned security group.** If CloudFormation gives up on it, the update still completes and the group stays in the account, outside the stack. Once `aws ec2 describe-network-interfaces --filters Name=group-id,Values=<security group id> --profile <profile>` returns none, delete it: `aws ec2 delete-security-group --group-id <security group id> --profile <profile>` Idle interfaces aren't charged meanwhile.

Read what you need from the Runtime log group **before** the rollback: outside `stage=prod` log groups are destroyed with their stack resource, so the switch back deletes `/aws/bedrock-agentcore/runtimes/<RuntimeId>-DEFAULT` (and a switch to `agentcore` deletes `/owlbank/ecs/tac-bridge`). Save `scripts/bench/call_latency.py` results first.

**What a reseed keeps.** `scripts/seed.py --reseed` (dry run first, then `--apply`) keeps the live values of these settings and prints each one that differs from the file; an `--overwrite-*` flag writes the file's value instead:
- **Masking** (`--overwrite-masking`): the `masking` item, silence fields included, and each tool's `mask`. It prints each difference as field, live value, seed-file value. A field missing from the table stays unset, and the bridge then uses its built-in default (the same values as `policy.json`).
- **Slot settings** (`--overwrite-slots`): each `slot#<name>` item's `sensitive`, `keypad_only`, `barge_in`, `mode`, `confirm` and `options`, the `slot_resolution` item, and the catalog's `option.*` spoken names. A field missing from the table takes the file's value.
- **Redaction** (`--overwrite-redaction`): the `redaction` setting (dropping a phase 1 `apply_to`, and turning an empty `entity_types` into `enabled: false`).
- **Catalog prompts** (`--overwrite-prompts`): a text edited in the console, or seeded before the seed hash existed, is kept and listed (key and language, never the text). A text you have not edited gets the seed file's text when it changed.

It **rewrites the rest**: each tool's level and confirmation mode, so copy console edits of those into `data/` first. Each item's `rev` is carried over and bumped, so an editor with the console open gets a 409 and reloads. Deploy all code first (front door, bridge, admin API), then reseed: code that predates a seed field can't read it. Pass `--developer-factor zip=NNNNN` (your own ZIP, dev and test only) on every dev reseed, or the ZIP reverts to the fixture's.

**Wait for the whole deploy before a test call.** A call made while one stack is new and the other old can behave in ways neither version does. Check that the bridge service's deployment is `COMPLETED` and the front door's `live` provisioned concurrency is `READY`.

## Deploy hazards

**Ordering and exports**

- **The bridge starts before Compute exists.** Stack order is Data, Network, Agent, BridgeImage, Bridge, Compute, Api, then the optional Admin. Until Compute deploys, `bank_tools` does not exist, so a bridge tool call would fail. No call can arrive in that window in the first-deploy order (Twilio's number is not pointed at the API until phase post), but a bridge that was deployed alone, or a Compute rollback, leaves tool calls failing until Compute is back.
- **Run the phase pre setup before the stacks.** Without `twilioOutputs` the bridge has no `TWILIO_CONVERSATION_CONFIGURATION_ID` and the front door and `auth_service` have no Conversation Configuration or Verify SID.
- **The relay parameter is read once per front-door environment, so the old value stays until Compute redeploys.** The front door and the warmer read `/owlbank/<stage>/bridge/relay` at start-up (INIT) and keep it; Compute does not import the CloudFront domain from Bridge. A missing or malformed parameter fails closed (`relay_parameter_unavailable`, every request fails). When the value changes without a Compute change (a replaced distribution, say), running environments, provisioned ones included, keep the old value: redeploy `OwlBankCompute` after the Bridge deploy, then re-run `twilio_setup.py --phase post` if the CloudFront domain is new. The Bridge's `*.cloudfront.net` name changes with the distribution, so every Twilio URL changes too. **A hosting switch** changes the value (relay host to Runtime ARN, or back) and Compute's template too, so always deploy Bridge and Compute together; the Bridge update removes the old hosting's resources before Compute is updated, so calls that arrive between the two reach the old relay and fail (apology, then a human) until the front door's new `live` environments are `READY`.
- **Do not rename `bank_tools` or `level0_tools`** (or their `function_name`s). They have fixed names (`owlbank-<stage>-bank-tools` and `-level0-tools`) so that the Agent and Bridge stacks name them by ARN. CloudFormation cannot replace a resource that has a fixed name (it would create the new one while the old one still holds the name), so a rename, or any change that forces replacement, fails the update. If a replacement is unavoidable, delete `OwlBankApi` and `OwlBankCompute` first (which also removes the Gateway's `level0_tools` target) and redeploy them.
- **Changing what a stack exports needs two deploys.** CloudFormation refuses to drop an export that another stack imports (`Cannot delete export ... as it is in use by ...`). Keep the old export with `self.export_value(...)` for one deploy, deploy the exporting stack and then the importing one, then remove the `export_value` line and deploy once more.
- **`--outputs-file` replaces the file.** A deploy of some stacks with `--outputs-file cdk-outputs.json` leaves only those stacks' outputs in it, and the seed and `scripts/masking.py` then can't find the tables. Use a separate file for partial deploys (`cdk-outputs-admin.json`, `cdk-outputs-agentcore.json`).
- **Wait a couple of minutes after an `OwlBankApi` deploy before the first call.** Right after a deploy that changes the API's integrations, API Gateway can return its generic 500 ("Internal server error", never reaching Lambda) for a minute or so while per-route Lambda permissions take effect.

**Hosting switch (`bridgeHosting`)**

- **A hosting switch drops calls in progress** (either direction): the Fargate tasks or the Runtime sessions go away with the Bridge update. Switch in a quiet period. After it, `twilio_setup.py --phase post` with the new deploy's outputs file moves the Orchestrator status callback (the `/webhook` relay URL or the `/voice/orchestrator` sink), and back on Fargate in the CloudFront mode the callback and the TwiML use the **new** distribution's domain; in the custom-domain mode, point `relay.<domain>` at the new ALB.
- **Every deploy repeats the hosting keys.** With `agentcore` deployed, a deploy of any stack without `-c bridgeHosting=agentcore -c bridgeImageDigest=...` synthesizes the Fargate shape, and if it includes Bridge or Compute (directly or as a dependency without `--exclusively`) it switches them back.
- **Production: the ALB has deletion protection.** At `stage=prod` the ALB is created with deletion protection, and a switch to `agentcore` removes the ALB from the Bridge template, which CloudFormation can't delete while the protection is on. Turning it off (`aws elbv2 modify-load-balancer-attributes --load-balancer-arn <arn> --attributes Key=deletion_protection.enabled,Value=false`) is a manual change to a production resource: do it just before the switch.
- **Switching to `agentcore` leaves the ALB log bucket behind.** The bucket is `RETAIN` with a generated name, so each switch away from Fargate leaves it in the account (its objects expire after 90 days), and a switch back creates a new one. Delete old ones by hand once their logs aren't needed.
- **`agentcoreNetworkMode=public` leaves `OwlBankNetwork` out of the app; it doesn't delete it.** A Network stack that was deployed stays, with its NAT gateway and its cost, and `cdk destroy` can't name a stack that isn't in the app: delete it with `aws cloudformation delete-stack --stack-name OwlBankNetwork` once the Bridge deploy in public mode is done (after a VPC-mode Runtime, its interfaces may still block the subnets, next item). A later switch to `fargate` or to VPC mode brings the stack back into the app; if it was deleted, that deploy creates a new VPC.
- **A VPC-mode Runtime is slow to delete.** Deleting `AWS::BedrockAgentCore::Runtime` can fail with "Request timed out while deleting" (`NotStabilized`) and finish on its own afterwards; a retry can then fail on the Runtime's security group ("has a dependent object") because two AgentCore-managed network interfaces (type `agentic_ai`, owned by the service) are still attached. You can't delete those; AgentCore releases them some time after the Runtime is gone (it can take up to about 1.5 hours). The Bridge update then stays in `UPDATE_COMPLETE_CLEANUP_IN_PROGRESS` on the security group, and because CDK deploys Compute and Api only after Bridge, the front door keeps the deleted Runtime's ARN and calls fail closed. So on a switch from `agentcore` VPC mode (back to Fargate, or to `public`), deploy Compute and Api from the synthesized assembly without waiting (`cdk deploy <stack> --app cdk.out --exclusively`, rollback step 2), and delete the orphaned group later, once `aws ec2 describe-network-interfaces --filters Name=group-id,Values=<security group id>` returns none. The Fargate bridge doesn't depend on these resources, and idle interfaces aren't charged.

**Settings and data**

- **Every Bridge deploy needs `-c twilioPhoneNumber`**, including a deploy of a stack that depends on the Bridge (Compute, Api, Admin) without `--exclusively`. If it is missing, on Fargate the new tasks crash at start-up and the circuit breaker rolls back; with `agentcore` synth fails, naming the key.
- **Deploy order for catalog and bridge changes that go together: reseed, then the bridge, in one sitting.** The catalog's `agent.system.*` texts, the `agent.caller_context*` keys and the bridge's code go together. Old bridge with the new catalog: the model gets no caller line, so no name or profile. New bridge with the old catalog: the old placeholders in the static text are stripped and the missing `agent.caller_context*` key is left out (`caller_context_missing`, WARNING). Neither window errors a call or sends caller data into the cached static part.
- **A call-state schema change must reach every writer together.** The `calls` item is written by the bridge (`OwlBankBridge`) and by the front door and `auth_service` (`OwlBankCompute`). Deploy a change to `owlbank.callstate` to both stacks together. Call state preserves attributes a writer doesn't know, so code with that rule can't drop a newer field, but a stale writer without it can: never run a stale `OwlBankCompute` beside a newer bridge.
- **A reseed undoes console edits to a tool's level or confirmation mode.** See "What a reseed keeps": copy those console edits into `data/` before a reseed. Masking, slot, redaction and catalog-prompt edits are kept unless you pass the matching `--overwrite-*` flag.
- **A deploy changes the agent's behavior in the middle of calls.** The catalog and the policy apply to the next turn of calls already in progress. Change them between test calls.

## Defaults that suit a first deployment, not production

- One bridge task (`bridgeDesiredCount=1`) and one NAT gateway.
- Always-on cost while idle: the NAT gateway, Lambda provisioned concurrency, the ALB, the Fargate task, the WAF web ACLs, CloudFront, the KMS keys and secrets, and the model poller. Tear down when you are done ("Clean up" in the README). Provisioned-concurrency arithmetic is in the production guide, "What provisioned concurrency costs".
- The Api stack replaces the account's per-Region API Gateway CloudWatch logging role, and `destroy` removes it; see the warning in step 10.
- Tables, secrets, KMS keys, the bridge ECR repository and the ALB log bucket are retained on stack delete in every stage (see "Clean up" in the README). Outside `stage=prod`, log groups are destroyed with their stack (1-month retention) and there is no deletion protection.
- The default security group is not restricted (`restrict_default_security_group=False`): CDK's custom resource for it adds a Node.js Lambda whose log group isn't CMK-encrypted. Nothing uses the default SG; restrict it in the account baseline.
- No Static Proxy IP allowlisting. The ALB (custom-domain mode), CloudFront and API Gateway accept any source on 443, behind WAF.
- **CloudFront mode (the default, no domain):** the CloudFront-to-ALB hop is HTTP (no ALB certificate), `execute-api` stays on, and the default certificate allows TLSv1 at the edge. Use the custom-domain mode for production (see the production guide).
- AgentCore Memory keeps call transcripts for 3 days, the service minimum.
